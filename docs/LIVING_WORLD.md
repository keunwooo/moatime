# 살아있는 월드 — 현재 구조 분석과 개선 설계 (Phase 1)

> 이 문서는 코드 수정 전에 작성한 **분석과 설계 제안**입니다. 이 문서를 쓰면서 소스 코드는 바꾸지 않았습니다.
> 성능 수치는 지난 개선(데이터 버전 2)의 검수에서 측정한 값입니다(`docs/IMPROVEMENT.md` 7절). "코드 확인"이라고 표시한 항목은 코드를 읽고 판단한 것이며 프로파일러로 측정하지는 않았습니다.

## 0. 요약

지금의 앱은 세 가지를 이미 갖추고 있습니다.

1. **누적 실행 시간 W**를 타임스탬프로 정확하게 계산하는 타이머
2. W의 순수 함수인 **결정적 작업 시뮬레이션**(숲지기·로버, 자원, 단계 건설)
3. 그 상태를 그대로 그리는 **PixiJS 2.5D 디오라마**

"집중 시간 = 월드 시간"의 뼈대는 이미 있습니다. 이번 개선의 방향은 다음과 같습니다.

- **월드 시간 계층 `src/world/` 신설.** 시뮬레이션 옆에 낮/밤·날씨·행성 환경·드문 사건·진행 단계를 둡니다. 모두 W와 시드의 순수 함수입니다. 새로고침이나 탭 전환, 세션을 어떻게 나누든 같은 W에서는 같은 세계가 보입니다.
- **장면을 시스템 단위로 분해.** 700줄짜리 테마 장면 두 개를 Sky / Weather / Vegetation / Wildlife … 시스템으로 나눕니다. 렌더 쪽에 우선순위와 동시 실행 상한을 가진 **Event Director**를 둡니다.
- **우주 테마는 같은 작업 엔진 위에서 다시 설계.** 작업자·단계·예약 회계는 재사용하고, 다음을 새로 얹습니다:
  - 자원 4종과 자원 노드 고갈
  - 6단계 건설과 콜로니 10단계
  - 정찰과 전초기지 확장
  - 결정적 습격, 피해, 수리, 재건
- **기존 사용자 진행은 보존.** 데이터 버전을 3으로 올립니다. 이관할 때 옛 규칙의 결과(완성 개수·시설 종류·진행 중 단위)를 기준점으로 고정합니다.

구현을 시작하기 전에 **11절의 결정 5가지**를 확인받고 싶습니다. 각 항목에 권장안을 적어 두었습니다.

## 1. 현재 구조 분석

### 1.1 전체 구성

```
React UI (src/app)                      ── 1Hz 이하로만 갱신 (상태 문구, 하단 통계, 자세히)
  │  engine.getState() / worldTime()
TimerEngine (src/core/engine.ts)        ── 세션·저장·탭 동기화, 애니메이션과 독립
  │  W = world.bankedMs + 열린 세션의 경과 시간 E
SimRunner (src/sim/runner.ts)           ── W까지 사건 단위 계산, 체크포인트(메모리 20분 간격, 저장 1개/테마)
  │  ForestSim / SpaceSim (W의 순수 함수)
SceneHost (src/scene/host.ts)           ── rAF 루프, 카메라 리그, FrameInfo 생성
  │  theme.framing(req), theme.update(frame)
ForestScene / SpaceScene                ── Backdrop + CardLayer(디오라마) + Overlay
```

### 1.2 타이머 상태 관리 (`src/core/engine.ts`, `session.ts`, `persist.ts`)

- 세션은 시작 시각과 일시정지 구간으로 기록합니다. 경과 시간 E는 `Date.now()`·`performance.now()` 타임스탬프로 계산하며, 애니메이션 프레임에는 의존하지 않습니다.
- 세션이 끝날 때 `world.bankedMs`에 한 번만 더합니다. 여러 탭은 Web Locks(`moa:v2:state` / `moa:v2:leader`)와 storage 이벤트의 rev 비교로 맞춥니다.
- 카운트다운·스톱워치·일시정지·완료 요약이 있습니다. 개발용 시간 조작(`devSetWorldTime`, 빠른 재생)도 있습니다.
- 분석 결론: **이번 작업에서 타이머 코드는 손대지 않습니다.** 새 월드 계층은 W만 읽습니다.

### 1.3 진행(progression) 상태 (`src/sim/`)

- `ForestSim`·`SpaceSim`은 (시드, `world.base`, `SIM_VERSION`, W)의 순수 함수입니다.
- 작업자는 Step `{k, a, b, t0, t1, n, c, ref, fx}`을 수행합니다. 재고는 단계가 끝나는 사건에서만 고정된 순서로 바뀝니다.
  - 분할 독립성: 5분×3과 15분×1의 결과가 같습니다.
  - 9시간을 무작위 400조각으로 나눠도 같습니다(테스트 통과).
- 단위·군락·구역: 4개 = 군락(전초기지), 4곳 = 구역입니다(`src/sim/units.ts`). 위치는 `nodePos(theme, seed, geom, id)`, 이동 시간은 `TravelTable`이 정합니다.
- 계절: `season.ts`에서 누적 120분이 1년입니다. 경계 5분은 보간합니다. 시뮬레이션은 낙엽 발생률에만 계절을 씁니다.
- 숲에 이미 있는 순환:
  - 씨앗 → 물 → 심기 → 돌봄 3회(부엽토 멀칭) → 성숙(약 12.6분)
  - 씨앗·낙엽 → 퇴비 → 부엽토
  - 빗물받이·물길·꽃밭, 다람쥐
- 우주에 이미 있는 순환:
  - 채굴 → 하역 → 비용 예약 → 현장 운반 → 7단계 조립(기초·바닥·골조·외벽·부품·전력·점검)
  - 시설 역할: 태양광=전력, 작업장=보조 로버, 안테나=광물 발견, 연결 거점=다음 구역

### 1.4 저장 방식 (`src/core/persist.ts`, `src/app/sim.ts`)

- localStorage에 다음 키를 씁니다. `?store=` 이름공간(`moa:${ns}:v2:...`)이 있어서 검수할 때 사용자 저장을 건드리지 않습니다.
  - `moa:v2:state`, 백업, 손상 보관
  - 이관 전 원본(`moa:v2:pre-migration`)
  - 테마별 시뮬레이션 체크포인트(`moa:v2:sim:<theme>`, 캐시)
- v1 → v2 이관은 저장된 v1 데이터의 순수 함수입니다. `base = {W, legacy:{units, partial}}`로 옛 결과를 고정하고, 이관은 멱등입니다.
- 체크포인트는 캐시일 뿐입니다. worldId·simVersion·theme·baseW가 모두 같을 때만 받아들이고, 없으면 W에서 다시 계산합니다.

### 1.5 컴포넌트 구조 (`src/app`)

- `App`: 전체 배치, 하단 통계와 "자세히"
  - `TopBar`: 테마, 설정 메뉴(애니메이션 / 효과 강도 / 자동 카메라 / 저전력 / 새 풍경)
  - `TimerPanel`: 시계, 입력, 상태 문구
  - `Summary`: 완료 요약
  - `SceneCanvas`: SceneHost 생성. 테마 장면 모듈은 lazy chunk로 불러옵니다.
  - `Poster`: WebGL이 없을 때의 정지 풍경
  - `DevPanel`: 개발 빌드 전용
- React는 프레임 단위 데이터를 다루지 않습니다. 상태 문구와 통계는 `useTicker`로 1초 이하 빈도로만 계산합니다.

### 1.6 렌더링 방식 — CSS / Canvas / SVG

| 기술 | 쓰는 곳 |
|---|---|
| **PixiJS 8 (WebGL)** | 배경 월드 전체. 캔버스 하나, `autoStart:false`로 직접 rAF 루프 |
| **Canvas 2D** | 텍스처 제작(과슈 붓 질감 `paint/brush.ts`). 테마를 만들 때 한 번 칠하고 GPU 텍스처로 올림. 매 프레임 Canvas 2D 그리기는 없음 |
| **Pixi Graphics** | 꿀벌, 충전 케이블 등 작은 도형 몇 개 |
| **CSS** | UI 전체(테마 토큰 `[data-theme]`, 시계 뒤 `.veil` 방사형 그러데이션, 메뉴). 배경에 CSS 애니메이션 없음 |
| **SVG** | 아이콘(`Icons.tsx`)만 |

디오라마는 이렇게 그립니다.
- `Projector`(원근 카메라)가 월드 좌표(X, Y, Z)를 화면에 투영합니다.
- `CardLayer`는 카메라를 향한 빌보드 카드를 먼 것부터 가까운 것 순서로 정렬해 둡니다. 매 프레임 투영·컬링·깊이 페이드를 합니다.
- `GroundSystem`(지면 띠), `HazeSystem`(안개 카드), `Backdrop`(하늘 텍스처 1장, 구름, 원경 언덕), `Overlay`(빛줄기·먼지·종이 질감)를 두 테마가 공유합니다.

### 1.7 애니메이션 구현 방식

시계가 세 개 있습니다. 이번 설계도 이 구분을 그대로 씁니다.

| 시계 | 무엇을 움직이나 | 성질 |
|---|---|---|
| **W** (월드 시간) | 작업자 위치·작업, 성장, 재고, 계절 | 결정적. 새로고침해도 같음. 일시정지하면 멈춤 |
| **t** (앰비언트 시계) | 바람, 구름 흐름, 반짝임, 새·나비 방문, 유성 | 장식. 일시정지·애니메이션 끔이면 멈춤 |
| **realT** | 완료 연출, 가림 페이드, 카메라 추종 | 화면 전용 |

- 애니메이션 끔(reduce)이면 1fps로만 그립니다. 일시정지 중에는 1초 간격입니다. 저전력은 약 30fps 상한입니다.
- 숨은 탭에서는 rAF가 그리기를 건너뜁니다. 다시 보이면 현재 W 상태로 바로 맞춥니다(snap).
- 앰비언트 사건(새·나비·유성)은 각 장면이 자체 타이머로 냅니다. 카메라가 움직이는 동안에는 미룹니다. **공통 스케줄러는 없습니다.**

### 1.8 Forest 구현 구조 (`src/scene/forest/`)

- `ForestScene.ts`(710줄)에 모든 것이 한 클래스에 들어 있습니다.
  - Backdrop(하늘 1장 + 구름 3 + 언덕), Ground/Haze/Overlay
  - 숲지기·다람쥐 보행
  - 꿀벌, 새·나비 방문, 낙엽 12장
  - 계절별 지면 틴트, 가림 페이드, 프레이밍
- `zone.ts`(697줄): 구역의 나무·공터·흙·낙엽 더미·눈 패치·장식을 sim에서 읽어 배치합니다.
- `tree.ts`(816줄): 나무 성장 모델입니다.
  - 계절은 덤불(clump)마다 지연을 두고 가을 텍스처로 교차 페이드합니다. **가을색은 수종별 한 가지**(금색·살구·장미)이고 초록→노랑→주황→빨강→갈색 단계는 없습니다.
  - 겨울 잔엽, 가지, 가지 끝 눈이 있습니다.
- **해는 화면 왼쪽 위에 고정되어 있습니다.** 빛줄기 각도도 고정(−0.62 rad)이고, 하늘은 한 장의 그러데이션 텍스처입니다.
- 없는 것: 낮/밤, 날씨, 비·눈 입자, 그림자 방향, 토끼·사슴·반딧불, 연못, 고목.

### 1.9 Space 구현 구조 (`src/scene/space/`)

- 설정은 **지구가 보이는 달 표면**입니다. 별 타일 + 반짝이는 별 6개, 지구 원반과 구름 흐름, 유성(45~120초 간격 앰비언트)이 있습니다.
- `SpaceScene.ts`(696줄)에는 다음이 들어 있습니다.
  - 로버 3대(단계에서 위치·바퀴 회전 산출)
  - 상자 운반 풀 8개, 먼지 풀 14개, 용접 불꽃
  - 충전 케이블(Graphics를 매 프레임 다시 그림)
  - 프레이밍, 가림 처리
- `outpost.ts`: 저장소 상자 더미(16칸), 광물 지대(고갈 표시), 착륙선·배터리
- `facility.ts`: 단계별로 올라오는 시설. `zone.ts`: 전초기지·시설·관·도로·안테나 표시
- 없는 것:
  - 자원 다양성(광물 1종 + 전력만 있음)
  - 콜로니 단계 구분
  - 정찰 연출
  - 전투, 피해, 수리, 재건
  - 행성 환경 사건
  - 혜성·가스 행성·위성 궤도·성운 움직임

### 1.10 성능 현황과 병목

이전 검수 측정값입니다(개발 빌드, 1440×820, GTX 1060).

| 누적 | 숲 fps / 프레임 CPU / 카드 | 우주 fps / 프레임 CPU / 카드 |
|---|---|---|
| 0시간 | 144 / 2.4ms / 1,241 | 144 / 2.4ms / 1,583 |
| 2,000시간 | 142 / 5.8ms / 2,103 | 143 / 5.0ms / 2,467 |

- 1,500시간을 한 번에 따라잡는 계산은 약 1초였습니다(한 번만, 이후 체크포인트).
- 번들: 메인 약 296KB, ForestScene chunk 약 84KB(압축 전).

코드에서 확인한 병목 후보입니다(측정 아님).

1. `CardLayer.project`는 모든 카드를 매 프레임 순회합니다(O(n)). 카드 수가 늘면 선형으로 증가하는 지금 가장 큰 고정 비용입니다.
2. `CardLayer.move`는 매 프레임, 움직이는 개체마다 `indexOf + splice + addChildAt`을 합니다(O(n)). 지금은 개체가 10개 안팎이라 괜찮지만, 야생동물·외계 유닛·방어 드론이 생기면 문제가 됩니다.
3. 프레임마다 생기는 배열 할당이 있습니다: `GroundSystem`의 정렬 배열, 가림 판정용 `occluders()` 배열 합치기.
4. 충전 케이블 같은 `Graphics`를 매 프레임 다시 그립니다(개수는 적음).
5. 테마 빌드 때 Canvas 2D 텍스처를 칠합니다. 시작 비용이고 프레임 비용은 아닙니다. 하늘·날씨·외계 텍스처를 추가하면 늘어납니다.
6. 큰 시간 점프 때 시뮬레이션 따라잡기가 있습니다(체크포인트로 완화됨).

### 1.11 새 요구와 현재 상태의 차이

| 요구 | 현재 | 처리 |
|---|---|---|
| 낮/밤 | 없음(해 고정) | 신규: `world/clock.ts`, 하늘 키프레임, 광원 틴트, 그림자 |
| 계절이 실제 상태를 바꿈 | 부분(단풍 1색, 눈 패치, 낙엽률) | 확장: 단풍 5단계 색 램프, 쌓이는 눈, 언 물, 꽃잎, 서리 |
| 날씨 상태 머신 | 없음 | 신규: `world/weather.ts` 스크립트형 상태 머신과 누적량(젖음·적설) |
| 숲 생명체 | 새·나비·벌·다람쥐 | 추가: 토끼, 반딧불, 사슴(드묾), 새 이동 |
| 숲 진행 1~10단계 | 나무·군락·구역·공터 시설 | 추가: 연못(숲지기가 파고 채움), 고목, 생태계 밀도 |
| 우주 RTS식 개척 | 로버 한 종류 순환 | 재설계: 작업 드론, 자원 4종, 6단계 건설, 콜로니 10단계 |
| 확장 | 다음 군락에 새 전초기지 | 보강: 정찰 드론 비행, 표시, 채굴 → 전력선 → 도로 연결 연출 |
| 전투·피해·수리·재건 | 없음 | 신규: 시뮬레이션 사건(결정적), 렌더는 계획 재생 |
| 동적 우주 배경·행성 환경 | 별·지구·유성 | 신규: 성운, 가스 행성, 위성 궤도, 소행성, 혜성 / 먼지 폭풍, 유성우, 태양 플레어, 오로라, 전기 폭풍 |
| 이벤트 우선순위와 동시 상한 | 없음 | 신규: 결정적 타임라인(월드 사건) + 렌더 Event Director(장식) |

---

## 2. 설계 원칙

1. **화면의 모든 "상태"는 W의 함수입니다.** 날씨, 하늘, 적설, 피해, 수리 진행, 콜로니 단계가 그렇습니다. 결정적이어서 새로고침해도 같습니다. 일시정지하면 세계도 멈춥니다.
2. **장식(움직임의 결)만 앰비언트 시계 t를 씁니다.** 빗방울 하나하나, 별 반짝임, 새의 날갯짓이 여기에 속합니다. 장식은 시뮬레이션 결과에 영향을 주지 않습니다. 효과 강도와 저전력은 장식에만 작용합니다.
3. **원인이 결과보다 먼저 보이게 합니다.**
   - 숲: 비 → 웅덩이·빗물받이 / 눈 → 쌓임 → 맑으면 녹음
   - 우주: 채굴 → 자원 → 건설 / 습격 → 피해 → 수리
4. **집중이 우선입니다.**
   - 큰 사건은 한 번에 하나만 보입니다.
   - 카메라는 사건을 쫓지 않습니다. 작업 구역 프레이밍을 유지합니다.
   - 번쩍임, 팝업, 보상 연출은 없습니다.
5. **기존 구조를 확장합니다.** 타이머·저장·탭 동기화는 그대로 두고, 시뮬레이션 엔진(Step/Worker/디스패처/러너)과 디오라마(CardLayer/Projector/카메라)는 재사용합니다.

## 3. 공통 월드 시간 계층 (`src/world/`, Phase 2)

렌더링이 없는 순수 모듈입니다. 단위 테스트 대상이고, 시뮬레이션과 장면이 함께 읽습니다.

### 3.1 시간 척도 (권장안, 11절 결정 1)

| 단위 | 누적 실행 시간 | 25분 집중 한 번에 보이는 것 |
|---|---|---|
| 숲의 하루 | **24분** | 해가 뜨고 지는 하루 한 바퀴(아침 → 낮 → 노을 → 밤 → 다음 아침 직전) |
| 우주 행성의 하루 | **32분** | 하루의 대부분. 빛의 방향이 바뀌고 지평선이 노을빛을 띰 |
| 계절 | **72분**(3일) | 계절 안의 변화(단풍 2단계, 적설 증가). 이따금 계절이 바뀜 |
| 1년 | **4.8시간** | 며칠에 걸친 사용에서 사계절이 순환 |
| 날씨 한 번 | 12~36분 | 맑음 → 흐림 → 비 → 갬 정도의 한 흐름 |

- 1시간 집중하면 하루 2.5번, 계절의 대부분, 나무 4~5그루(군락 하나)가 보입니다. 우주에서는 시설 6~7개와 콜로니 단계 1~2개가 진행됩니다.
- 새 세계(W=0)는 **봄의 이른 아침, 맑음**으로 시작합니다.
- 밤은 하루의 약 25%(6분)입니다. 깊은 어둠은 피하고 달빛 파스텔로 그립니다(7.4절 대비 기준).

### 3.2 낮/밤 — `clock.ts`

```ts
dayAt(theme, W) → {
  day: number,           // 며칠째
  p: number,             // 하루 위상 0..1 (0 = 자정)
  phase: 'night' | 'dawn' | 'day' | 'dusk',
  sun: { elev, azim, x, y },        // 고도 −1..1, 화면 궤적(동→서)
  moon: { elev, x, y, illum },      // 위상(29일 주기) 포함
  light: { color, intensity, ambient, shadowLen, shadowDir },
  sky: [w_night, w_dawn, w_day, w_dusk],   // 하늘 키프레임 가중치(합 1)
  stars: number,         // 별 투명도 0..1
}
```

- 태양 궤적은 다항식 근사를 씁니다. 시뮬레이션은 낮/밤을 쓰지 않으므로 렌더 쪽에서는 `Math.sin`을 써도 됩니다.
- 하늘 키프레임 경계는 각각 1~2분에 걸친 smoothstep 보간입니다.

### 3.3 계절 — `season.ts`

- 지금의 `src/sim/season.ts`를 `src/world/season.ts`로 옮기고 주기를 `SEASON.yearMs`로 설정합니다.
- 보간 구간을 5분에서 8분으로 늘립니다(계절이 길어짐에 맞춤).
- `seasonMix`에 **계절 내부 진행 곡선**을 추가합니다.
  - 가을 단풍 램프 `autumnHue(p)`: 초록 → 노랑 → 주황 → 빨강 → 갈색
  - 겨울 서리 강도, 봄 꽃 개화 정도

### 3.4 날씨 상태 머신 — `weather.ts`

자유로운 마르코프 체인 대신 **블록 스크립트 방식**을 씁니다. O(1) 순수 함수이고 결정적이며, 인접 상태로만 전이하는 것이 보장됩니다.

- 시간을 블록(약 36분)으로 나눕니다. 블록 b의 스크립트는 `hash(seed, b)`와 그 블록의 계절 가중치로 고릅니다. 모든 스크립트는 CLEAR나 CLOUDY에서 시작해 CLEAR나 CLOUDY로 끝나므로 블록 경계도 이어집니다.
- 스크립트 예:
  - 봄비: `CLEAR → CLOUDY → LIGHT_RAIN → CLOUDY → CLEAR(+무지개 후보)`
  - 여름 소나기: `CLOUDY → HEAVY_RAIN → STORM → HEAVY_RAIN → LIGHT_RAIN → FOG → CLEAR`
  - 가을 돌풍: `CLEAR(바람 강) → CLOUDY → LIGHT_RAIN → CLEAR`
  - 겨울 눈: `CLOUDY → SNOW → SNOW(강) → CLOUDY → CLEAR(햇빛에 일부 녹음)`
  - 아침 안개: `FOG → CLEAR` (dawn에 맞춤)
- 상태마다 연속 강도가 있습니다: `{cloud, rain, snow, fog, wind, dark}`. 상태 사이 전이(2~4분)는 smoothstep으로 보간합니다. 화면은 상태 이름이 아니라 이 연속값을 그립니다. 그래서 급전환이 없습니다.
- 번개: STORM 구간 안에서 `hash`로 정해지는 타격 시각입니다(최소 간격 8초, 10초에 2회 이하). 결정적이지만 렌더에서만 씁니다.
- **누적량**(최근 블록의 구간별 적분, O(구간 수))
  - `wetness(W)`: 비가 오면 오르고 맑으면 약 10분에 걸쳐 마릅니다 → 웅덩이·젖은 지면
  - `snowCover(W)`: 겨울 SNOW 동안 쌓이고 맑은 낮에 일부 녹으며, 봄이 되면 사라집니다 → 지면 눈의 양, 나무 위 눈, 언 물
- 첫 블록은 항상 맑음입니다. 첫인상과 첫 작업이 잘 보이게 하기 위해서입니다.
- 우주(`planet.ts`)도 같은 블록 방식입니다: `CALM / DUST / DUST_STORM / ELECTRIC / FLARE / AURORA(밤)`.

### 3.5 월드 타임라인 — `timeline.ts` (결정적 사건과 우선순위)

드문 사건과 습격처럼 "실제로 일어난 일"은 W에 묶인 결정적 사건입니다.

- 우선순위: `COMBAT(4) > RARE(3) > WEATHER(2) > AMBIENT(1) > NORMAL(0)`
- 후보 생성:
  - 블록마다 `hash(seed, block, kind)`로 후보를 만듭니다.
  - 자격 조건을 봅니다: 진행 단계, 계절, 시간대, 날씨(예: 무지개 = 봄비 직후의 낮, 사슴 = 단계 8 이상의 새벽이나 노을).
  - 배제 규칙: 동시에 하나만, 최소 간격(드문 사건 90분, 습격 50분), 습격 ±3분 안에는 드문 사건 없음.
- 결과 `eventsIn(theme, seed, W0, W1)`는 `{kind, priority, t0, t1, params}` 목록이고 정렬되어 있습니다.
- 습격처럼 시뮬레이션에 영향을 주는 사건은 시뮬레이션이 같은 함수를 읽어 사건으로 처리합니다(6.7절). 무지개처럼 장식뿐인 사건은 장면만 읽습니다.

### 3.6 진행 단계 — `stage.ts`

`forestStage(sim)`·`spaceStage(sim)`은 1~10을 돌려줍니다. 시간이 아니라 **시뮬레이션 사실**(완성 수, 연못, 고목, 기지 수)에서 계산합니다(5.6절, 6.5절). 단계는 이벤트 자격 조건, 화면 복잡도(Progressive Detail), 상태 문구에 씁니다.

### 3.7 `worldEnv(theme, seed, W, sim)`

위의 모든 값을 한 번에 계산합니다. 호스트가 프레임마다 한 번 호출해 `FrameInfo.env`로 넘깁니다. 상태 문구 같은 UI도 같은 함수를 1Hz로 읽습니다.

## 4. 렌더링 구조 (Phase 2에서 뼈대, 이후 단계에서 채움)

### 4.1 레이어

요구한 레이어 구조를 Pixi 컨테이너 순서에 대응시킵니다. 깊이 정렬이 필요한 것은 기존처럼 CardLayer 안에서 Z로 섞습니다.

```
World (theme.root)
├─ BackgroundLayer   우주: 성운·가스 행성·위성·소행성 / 숲: 먼 하늘 키프레임 (Backdrop 확장)
├─ SkyLayer          해·달·별·구름·무지개·오로라·번개 빛 (screen-space)
├─ WeatherLayer(far) 먼 비·눈 장막, 안개 띠 (HazeSystem 확장)
├─ EnvironmentLayer  원경 언덕(시간대 틴트), 지면 띠(젖음·적설 틴트)          ┐
├─ EntityLayer       숲지기·다람쥐·동물 / 드론·외계 유닛 (CardLayer 카드)     │ CardLayer
├─ BuildingLayer     나무·공터 시설 / 기지 건물, 피해 오버레이 (CardLayer 카드)  │ (Z 정렬)
├─ ParticleLayer     낙엽·꽃잎·불꽃·먼지 (깊이가 필요한 소수만 카드)          ┘
├─ WeatherLayer(near) 비 줄기·눈송이 (ParticleContainer, 화면 공간 3겹 깊이)
├─ EventLayer        유성·혜성·우주선 등 드문 사건 (screen-space)
└─ ForegroundLayer   빛줄기·먼지·종이 질감·밤/플레어 색 보정 (Overlay 확장)
```

**LightRig**(신규)는 시간대와 날씨 광원을 다음에 적용합니다.
- 디오라마 컨테이너 틴트(Pixi v8 컨테이너 tint는 자식에 곱해짐): 식물 색감과 밤의 푸른빛
- 원경 언덕 틴트, 지면 틴트(이미 있는 `GroundSystem.tint`)
- 빛줄기 각도와 위치(해 위치를 따라감)
- 그림자: 키 큰 카드(나무·건물)에 기울인 타원 그림자 스프라이트를 1장씩 둡니다. 길이와 방향은 태양 고도와 방위에서 나옵니다. 상세 구역에만 둡니다.

### 4.2 시스템 인터페이스와 장면 분해

```ts
interface WorldSystem<Sim> {
  build(ctx: SystemCtx): void | Promise<void>;
  update(f: WorldFrame<Sim>): void;     // f = FrameInfo + { sim, env, director }
  destroy(): void;
  stats?(): Partial<SceneStats>;
}
```

- `ForestScene`과 `SpaceScene`은 시스템들을 순서대로 호출하는 **조립자**가 됩니다. 기존 코드는 해당 시스템 파일로 옮깁니다(동작 변경 없이 먼저 이동하고 비교 스크린숏으로 확인).
- ForestWorld: `SkySystem`(하늘·해·달·별) · `DayNightSystem`(LightRig·그림자) · `SeasonSystem`(나무 setSeason·지면·꽃잎·서리) · `WeatherSystem`(강수·안개·번개·젖음·적설) · `VegetationSystem`(zone·tree) · `WildlifeSystem`(숲지기·다람쥐·새·나비·벌·토끼·반딧불·사슴) · `AmbientEffectSystem`(낙엽·먼지·빛줄기)
- SpaceWorld: `SpaceBackgroundSystem` · `PlanetEnvironmentSystem` · `ResourceSystem` · `WorkerSystem` · `ConstructionSystem` · `ColonySystem`(도로·전력선·네트워크) · `CombatSystem` · `RepairSystem` · `SpaceEventSystem`

### 4.3 Event Director (`src/scene/director.ts`)

결정적 타임라인(3.5절)은 "무엇이 일어났는가"를 정합니다. Director는 "**지금 화면에 동시에 얼마나 보일 것인가**"를 정합니다.

- 채널과 상한(기본 효과 강도 기준):

  | 채널 | 동시 상한 | 예 |
  |---|---|---|
  | headline | 1 | 습격, 드문 사건, 행성 환경 정점 |
  | weather | 1 상태 | 강수·번개 (입자 예산 안에서) |
  | fx | 1 | 유성, 꽃잎 바람, 우주선 통과 |
  | ambient | 2 | 새, 나비, 토끼, 소행성 |

- 우선순위 규칙:
  - headline이 진행 중이면 fx와 ambient는 새로 시작하지 않습니다(진행 중인 것은 자연스럽게 끝냅니다).
  - 폭풍과 습격 중에는 나비·새 방문을 멈춥니다.
- 조용히 할 때: 카메라 이동 중, 핵심 작업 순간(새싹 트임, 부품 장착), 애니메이션 끔, 일시정지.
- **입자 예산**: 프레임 전체 상한(예: 기본 420, 풍부 600, 낮음 200, 저전력 ×0.6)을 채널 우선순위대로 나눠 줍니다.
- 기존 장면별 타이머(새·나비·유성)를 Director 요청으로 바꿉니다. 지금의 "카메라 이동 중 미룸" 규칙은 그대로 Director 규칙이 됩니다.

### 4.4 공용 부품

- `ParticleField`: Pixi v8 `ParticleContainer`와 `Particle` 풀입니다. 비 줄기, 눈송이, 꽃잎, 먼지, 불꽃을 처리합니다. 화면 공간 3겹(먼·중간·가까운) 깊이를 크기·속도·투명도로 표현합니다. 개체마다 CardLayer 카드를 만들지 않습니다.
- `SkyLayer`:
  - 하늘 키프레임 텍스처 5장(밤·새벽·낮·노을·흐림, 각 64×1024 그러데이션)을 두 장씩 교차 페이드합니다.
  - 해·달 원반, 별장(밤에만 투명도), 구름 3~6장(덮임 정도와 속도는 날씨에서)
- `Pool<T>`: 카드와 스프라이트 재사용(유닛·동물·투사체)
- `CardLayer.move` 빠른 경로: 이웃 카드와 순서를 비교해 대부분 O(1) 교환으로 처리합니다(8절).

## 5. Forest 설계 (Phase 3·4)

### 5.1 낮과 밤 (Phase 3)

| 시간대 | 하늘 | 빛·그림자 | 대기 | 생명 |
|---|---|---|---|---|
| 새벽 | 연보라 → 복숭아빛, 동쪽 지평선 밝아짐 | 낮은 금빛, 긴 그림자 서쪽으로 | **푸른 아침 안개**(haze ↑) | 새가 깨어남 |
| 낮 | 맑은 하늘색 | 밝은 초록 숲(틴트 중립), 짧은 그림자 | 안개 ↓ | 나비·벌 |
| 노을 | 주황 → 장미빛 | **주황 햇빛 + 긴 그림자** 동쪽으로, 빛줄기 낮게 | 따뜻한 안개 | 새가 둥지로 |
| 밤 | 남색 파스텔, 별, 달(위상 변화) | 푸른 달빛 틴트, 약한 달 그림자 | 차가운 안개 | **반딧불**(여름 밤 많이), 공터 시설의 작은 등불 |

- 숲지기는 밤에도 일합니다. 작업 결과가 시간대와 무관해야 하기 때문입니다. 대신 밤에는 등불을 들고 다닙니다(시각만 변경).

### 5.2 계절 (Phase 3)

| 계절 | 상태 변화 | 동적 사건 |
|---|---|---|
| 봄 | 연한 초록 잎, 꽃나무 개화(`blossom` 수종), 들꽃 밀도 ↑, 새 등장 | 꽃잎이 바람에 날림, 봄비, 웅덩이, 갠 뒤 햇빛, 무지개(드묾) |
| 여름 | 잎 풍성, 짙은 초록, 강한 햇빛, 빠른 구름, 곤충, 밤 반딧불 | 소나기, 천둥·번개(부드러운 빛), 잎에서 떨어지는 빗방울, 갠 뒤 수증기·안개 |

- 단풍 색 램프: 가을 덤불 텍스처를 **밝은 중성색으로 한 번만 칠합니다**. 색은 스프라이트 tint로 램프를 따라 바꿉니다. 텍스처는 늘지 않습니다.
- 적설: 기존 눈 패치 34개를 `snowCover`에 따라 단계적으로 드러냅니다. 지면 띠 틴트와 나무 눈 모자 투명도도 같은 값에서 나옵니다.

### 5.3 날씨 표현 (Phase 3)

- 구름 덮임은 하늘 키프레임 "흐림" 가중치와 구름 개수·투명도를 높이고 광량을 낮춥니다.
- 비:
  - 근경 비 줄기 3겹(ParticleField), 원경 비 장막(haze 카드에 사선 텍스처)
  - 지면 젖음(틴트 진하게), 웅덩이(공터 근처 고정 위치 6~10곳이 `wetness`에 따라 커짐)
  - 빗물받이 수위
- 폭풍: 어두움, 바람(기존 `forestWind` 진폭에 날씨 바람을 곱함), 번개(하늘 영역만 짧게 밝아짐, 7.1절 제한)
- 안개: HazeSystem의 투명도와 시작 깊이를 당깁니다. 단, 작업 구역 앞은 가리지 않습니다(지금처럼 `minDepth`는 현장 뒤).
- 눈: 느린 눈송이, 바람 따라 흔들림
- **시뮬레이션 연결**(작은 인과): 비가 오는 동안 빗물받이가 더 빨리 찹니다(`barrel.fillEveryMs`에 강수 계수). 숲지기가 이미 물길을 쓰는 순환에 "비 → 물"이 보이게 됩니다. 결과는 W와 시드로 결정됩니다.

## 6. Space 설계 (Phase 5~9) — "작은 개척지에서 행성 문명으로"

### 6.1 설정과 미감 (11절 결정 2)

- **달기지에서 이름 없는 외계 행성으로 바꿉니다.** 먼지 폭풍·오로라·전기 폭풍에는 대기가 필요하기 때문입니다.
  - 하늘은 지금처럼 어둡게 둡니다. 엷은 대기라서 별과 성운이 보입니다.
  - 하늘에 고리 가스 행성과 작은 위성이 있습니다.
  - 지면은 지금의 파스텔 과슈 질감을 유지하고, 색은 황토·장미빛 모래로 바꿉니다.
- 독자 미감: 둥근 모서리의 모듈, 따뜻한 창문빛, 천 같은 차광막, 손으로 칠한 질감입니다. 스타크래프트의 유닛·건물 실루엣, 이름(미네랄·가스·SCV 등), 색 조합(파랑 수정 + 녹색 가스, 금색 + 청색 사이오닉, 보라 갑각)은 쓰지 않습니다.
- 테마 이름은 **"우주" 그대로** 둡니다(결정 2). 달을 전제로 한 소개 문구(`index.html`·FAQ·OG 설명)만 Phase 10에서 행성 개척지에 맞게 고칩니다.

### 6.2 작업자 (Phase 5)

- **작업 드론**: 지금의 로버 차체를 바탕으로 다시 그립니다. 낮은 바퀴 차체, 적재함, 작업 팔, 머리 등이 있고 자원 색이 보이는 화물칸을 답니다.
- 처음에는 **2기**입니다(콜로니 1단계: 착륙선 + 드론 2). 사령부와 공장이 늘려 최대 6기까지 갑니다.
- 기존 루프 `기지 → 자원 → 채굴 → 운반 → 기지`를 그대로 씁니다. 디스패처 우선순위는 다음 순서입니다.
  1. 대피(태양 플레어)
  2. 수리
  3. 재건
  4. 건설 단계
  5. 운반
  6. 채굴
  7. 정찰
  8. 충전
  9. 대기
- 배터리·충전, 전력망은 지금 모델을 유지합니다.
- **Phase 5에서 구현한 것**(대피·수리·재건·정찰은 Phase 7·8)
  - 우선순위: 건설 단계 → 운반 → 채굴(앞으로 지을 건물 몫까지) → 조립 돕기 → 온실 → 점검 순회 → 충전 → 대기
  - 채굴: 드론이 둘 이상이면 이 전초기지의 다음 건물 최대 3채 몫까지 미리 캡니다. 저장소에 자리가 있을 때만 캡니다.
  - 조립 돕기: 다른 드론이 조립 중인 단계를 반대편 모서리에서 함께 작업합니다. 한 번에 한 기만 돕고, 걸리는 시간은 바뀌지 않습니다(화면용).
  - 점검 순회: 근처 완성 건물을 하나씩 돌아보며 스캔합니다. 한 번에 한 기만 돕니다(Phase 8 수리의 자리).
  - 처음 두 기는 4초 간격으로 출발해 한 몸처럼 움직이지 않습니다.
  - 차체는 지금 로버를 그대로 쓰고, 화물칸에 자원 색을 입혔습니다. 차체를 새로 그리는 일은 Phase 6 건물 그림과 함께 합니다.

### 6.5 콜로니 진행 1~10 (Phase 6·7)

건설 순서는 결정적 표로 정합니다(지금 `planKind` 자리).

| 단계 | 조건 | 생기는 것 | 대략 시점 |
|---|---|---|---|
| 1 착륙선 | W=0 | 착륙선, 드론 2 | 0 |
| 2 채굴기·발전기 | 1~2번째 건물 | 금속 채굴기, 발전기 | 약 20분 |
| 3 거주·저장 | 3~4번째 | 거주 모듈, 저장소 | 약 40분 |
| 4 사령부 | 5번째 | 사령부(드론 +1, 콜로니 이름 표시) | 약 50분 |
| 5 연구 | 6~7번째 | 결정 채굴기, 연구 시설(희귀 광물 탐지, 정찰 드론) | 약 1시간 |
| 6 방어 포탑 | 8번째 | 포탑(이후 습격 가능) | 약 1.2시간 |
| 7 공장 | 9번째 | 공장(드론·방어 드론 생산) | 약 1.4시간 |
| 8 여러 기지 | 다음 군락으로 확장 | 새 자원 지역 전초기지(6.6절) | 약 1.7시간 |
| 9 행성 네트워크 | 구역 1 완성 | 중계탑, 위성 접시, 기지 사이 도로·전력선, 위성 발사(드문 사건) | 약 2.5시간 |
| 10 행성 문명 | 구역 3 이상 | 돔 도시, 탑, 셔틀 왕래, 밤의 도시 불빛이 원경 언덕까지 | 10시간 이상 |

- 축소해서 보면 행성 곳곳에 기지, 채굴 지역, 전력망, 도로, 전력선, 방어 시설, 위성 접시가 이어져 있습니다. 지금 원경 언덕에 쓰는 "정착지 불빛" 장식을 구역 수에 따라 늘리는 방식을 확장합니다.
- **Phase 6에서 구현한 것**: `spaceStage(sim)`(1~10, 내려가지 않음)
  - 판정 기준
    - 1~7단계: 서 있는 건물 종류
    - 8단계: 넷째 전초기지
    - 9단계: 구역 1 완성 + 중계탑
    - 10단계: 구역 3 시작
  - 사령부가 서면 콜로니 이름이 생깁니다. 시드로 정해지고 "자세히"에 보입니다(예: "새벽별 개척촌").
  - 측정(시드 424242·7·99)

    | 단계 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 | 10 |
    |---|---|---|---|---|---|---|---|---|---|
    | 시점 | 17~18분 | 32분 | 43~44분 | 50~51분 | 63~65분 | 80~82분 | 93~96분 | 122~124분 | 355~357분 |

  - 8~10단계의 모습(정찰·연결 공사·돔 도시)은 Phase 7에서 채웁니다.

### 6.6 확장 (Phase 7)

```
기존 기지 → 정찰 드론 비행(하늘 낮게) → 새 자원 지역 탐색(스캔 원) → 전초기지 표지 착륙
 → 채굴 시설 → 전력선 연결(전 기지에서 이어 깔기) → 도로 연결 → 본 기지 네트워크 편입
```

- 지금 구조의 "다음 군락 = 새 전초기지"와 "안테나 = 광물 발견"을 그대로 씁니다. 정찰 비행과 연결 공사를 실제 작업 단계로 추가해 보이게 합니다.
- 카메라: 확장 순간에는 기존 `outpost` 프레이밍으로 두 기지 사이를 넓게 잡습니다. 그 뒤 새 작업 구역으로 천천히 옮깁니다.
- **Phase 7에서 구현한 것**
  - 정찰(`sim.scout`, 연구 시설이 선 뒤)
    - 전초기지가 완성되면, 공개 구도를 잠시 보여 준 뒤(24초) 정찰 드론이 이륙합니다.
    - 새 자리로 16초 날아가고, 9초 동안 한 바퀴 돌며 스캔합니다. 땅에서 청록 고리가 퍼집니다.
    - 3초 동안 표지(삼각대 등대)를 내려놓고 떠납니다.
    - 표지가 내려앉기 전에는 아무도 저장소 자리를 표시하지 않습니다.
    - 정찰 스캔이 광맥을 찾으므로 지상 조사는 생략됩니다. 연구 전(둘째 전초기지)에는 지금처럼 드론이 지상 조사를 합니다.
  - 전력선(`link` 작업): 저장소 자리 표시가 끝나면 드론 한 대가 앞 전초기지 저장소로 돌아가 새 저장소까지 전력선을 깔며 기어 옵니다(주행의 2.6배 시간). 다른 드론들은 그동안 새 광맥을 캡니다.
  - 카메라
    - 정찰 중에는 새 자리를 잡고, 정찰 드론이 화면 밖에서 날아 들어옵니다. 처음 설계처럼 두 기지를 함께 잡으면 너무 멀어져 정찰 드론이 몇 픽셀로 보였습니다.
    - 전력선을 까는 동안에는 드론 앞쪽 구간을 다섯 번에 나눠 천천히 따라갑니다.
  - 원경 네트워크: 먼 구역(상세 구역 뒤)마다 전초기지 사이와 다음 정착지까지 불 켜진 길이 이어집니다.
  - 9단계부터는 70~140초에 한 번 셔틀이 먼 정착지에서 이륙해 화면 옆으로 날아갑니다. 타이머 양옆 3분의 1 구역만 지납니다.

### 6.7 습격·방어·피해·수리·재건 (Phase 8)

**언제 일어나는가 (결정적)**
- 방어 포탑을 지은 뒤부터 일어납니다(콜로니 6단계). 첫 습격은 포탑 완공 15~25분 뒤입니다.
- 그 뒤에는 누적 실행 50~90분에 한 번입니다(`timeline.ts`, 시드 해시). 다른 headline 사건과 겹치지 않습니다.
- W에 묶여 있으므로 **타이머가 돌 때만** 일어납니다. 자리를 비운 동안이나 일시정지 중에는 일어나지 않습니다.

**두 외계 세력 (독자 디자인)**

| 세력 | 성격 | 모습 | 쓰러질 때 |
|---|---|---|---|
| 모래 떼 (Swarm) | 작고 빠른 다수(8~14) | 둥근 등딱지의 모래색 소형 생물, 무리 지어 물결처럼 이동 | 몸을 말고 굴러 달아나거나 모래 먼지로 흩어짐(피·잔혹 표현 없음) |
| 빛 수호체 (Advanced) | 소수(2~4)의 강한 에너지 개체 | 떠다니는 반투명 다면체 껍질과 희미한 방어막 고리, 느린 빛 구슬 발사 | 방어막이 깜빡이다 사라지고, 빛이 접히며 순간 이동으로 물러남 |

**방어 — 탱크와 보병, 쌓이는 병력 (결정 3)**
- 콜로니가 병력을 기릅니다. 심시티처럼 시간이 쌓이면 주둔군이 늘어나는 것이 보입니다.
  - **병영**(콜로니 6단계): 자원(금속·에너지)을 써서 보병을 한 명씩 훈련합니다. 훈련된 보병은 연병장에 줄을 서고, 기지 둘레를 순찰합니다.
  - **차량 정비고**(공장과 함께, 7단계): 금속·결정으로 탱크를 한 대씩 조립합니다. 탱크는 정비고 앞 주차 구역에 늘어섭니다.
  - 훈련과 조립도 작업자 단계처럼 시뮬레이션 사건입니다. 결정적이며 상한이 있습니다(기지당 보병 24, 탱크 8까지 화면에 표시, 그 이상은 다음 기지 주둔군으로 배치).
- 보병: 둥근 헬멧과 등 배낭을 단 작은 개척민 경비대. 소총 대신 짧은 빛줄기(테이저 광선)를 쏩니다.
- 탱크: 낮고 넓은 바퀴형 차체와 짧은 포신을 가진 독자 디자인. 느리게 회전하는 포탑에서 빛 탄을 쏩니다.
- 포탑(회전, 가는 레이저 줄과 느린 탄)과 방어막 발전기(반투명 돔)도 있습니다.
- 습격이 오면 주둔군이 위협 쪽 기지 외곽으로 이동해 대열을 짓고, 습격이 끝나면 연병장과 주차 구역으로 돌아갑니다.
- 습격의 규모는 콜로니 크기와 주둔군 규모에 맞춰 정해서, 병력이 늘어나는 의미가 있게 합니다.

**전투의 길이와 크기**
- 접근 25초 + 교전 40~60초 + 후퇴 15초, 합쳐 약 1.5분입니다.
- 화면 가장자리 쪽 기지 외곽에서 작게 일어납니다. 발사 간격은 포탑당 1.2초 이상입니다.
- 카메라는 전투를 쫓지 않습니다. 상태 문구에는 "북쪽 전초기지에 모래 떼가 접근해요 — 포탑이 막고 있어요." 정도만 나옵니다.

**결과의 결정성**
- 습격 시작 사건에서 그 시점의 시뮬레이션 상태(방어 수, 목표 기지)와 해시로 **습격 계획**을 한 번 만듭니다.
  - 계획은 접근 경로, 발사·명중 시각, 어떤 건물·방어 유닛이 얼마나 피해를 입는지를 담습니다.
- 시뮬레이션은 계획의 피해 사건만 처리합니다(정수 ms). 렌더는 계획을 W로 재생합니다.

**유닛 피해**
- 탱크·포탑: HP 감소 → 연기 → 불꽃 → 파괴 → 잔해. 작은 불꽃과 연기 한 줄기, 금속 조각 3~5개 정도로 표현하고, 큰 폭발과 화면 흔들림은 없습니다. 잔해는 작업 드론이 정리하고 정비고가 다시 조립합니다.
- 보병: 쓰러지거나 죽는 연출은 없습니다. HP가 다하면 그 자리에 앉아 보호막 캡슐을 펼치고, 구급 드론이 병영으로 데려갑니다. 일정 시간 뒤 다시 대열로 돌아옵니다.

**건물 피해 상태**

| 상태 | 표시 |
|---|---|
| 정상 | — |
| 경미 | 패널 한두 장 어긋남 |
| 연기 | 지붕에서 연기 한 줄기 |
| 불꽃 | 깨진 패널 + 간헐 불꽃, 안테나 기울어짐, 창문 일부 꺼짐 |
| 위험 | 대부분 소등, 구조물 노출 |

- 지금 단계별 시설 그림에 **피해 오버레이 스프라이트**를 얹어 표현합니다. 건물마다 새로 칠하지 않습니다.

**수리**
- 습격이 끝나면 디스패처가 수리를 건설보다 먼저 맡깁니다.
- 순서: 드론 도착 → 수리(용접 불꽃) → 패널 복구 → 조명 복구 → 가동
- 시간은 피해량에 비례하고(1~3분), 금속을 조금 씁니다.

**재건**
- 위험 상태에서 추가 피해를 받으면 잔해가 됩니다. 드문 경우로 제한합니다(습격 6회에 1회 이하, 사령부·착륙선은 제외, 습격당 건물 하나까지).
- 순서: 드론이 잔해를 정리(잔해 상자를 저장소로, 재료 절반 회수) → 기초부터 다시 건설(기존 건설 파이프라인을 "재건 프로젝트"로 재사용, 새 건물보다 우선)

**진행 보호**
- 피해를 입거나 재건 중인 건물도 콜로니 단계와 완성 수에서는 지은 것으로 칩니다. **콜로니 단계는 내려가지 않습니다**(11절 결정 4).

**Phase 8에서 구현한 것과 설계와 달라진 점**
- 시뮬레이션(`sim/raid.ts`, `sim/space.ts`, `SIM_VERSION` 9)
  - 습격 계획은 시작 순간 한 번 만듭니다. 시드, 습격 번호, 그 순간의 방어(포탑, 전선에 나간 탱크·경비대)로 정합니다.
  - 계획에 담기는 것
    - 습격자마다 쫓겨나는 시각
    - 건물별 피해 단계와 그 시각
    - 무력화되는 탱크, 보호막에 드는 경비대원
    - 잔해(-1이면 없음)
  - 개별 사격은 저장하지 않고, 장면이 계획에서 결정적으로 만들어 냅니다.
  - 시뮬레이션 사건 고리에 "콜로니 사건"을 넣었습니다. 훈련, 경비대원 복귀, 습격 시작, 습격 끝이 드론 사건과 같은 정수 ms 순서로 처리되므로, 시간을 어떻게 나눠도 결과가 같습니다.
  - 습격 규모는 구역과 습격 횟수에 따라 커집니다. 피해 정도는 공격/(공격+방어) 비율에 시드 흔들림을 더해 정합니다. 그래서 주둔군이 가득 차도 가벼운 피해는 이어집니다.
  - 잔해는 80개 시드 × 6시간에서 습격 348번 중 7번(2%)이었고, 모두 방어가 약한 첫 습격이었습니다.
- 주둔군: 병영이 4분마다 경비대원 한 명, 공장이 9분마다 탱크 한 대를 만듭니다.
  - 건물 두 채까지는 빨라지고, 상한은 경비대 24·탱크 8입니다.
  - **설계와 다른 점**: 훈련에 자원을 쓰지 않습니다. 시간과 건물만으로 늘어납니다.
- 연병장은 지금 일하는 전초기지 옆(퇴적층 반대쪽)에 있어, 일하는 구도에서 병력이 쌓이는 모습이 보입니다. 두 명은 저장소 쪽을 천천히 돌며 순찰합니다.
- 전선은 퇴적층 바로 너머입니다.
  - 경비대는 네 명씩 줄을 지어 서고, 탱크는 그 뒤에 둘씩 섭니다.
  - 모래 떼는 물결처럼 다가왔다 물러나고, 빛 수호체는 떠서 느린 빛 구슬을 건물에 쏩니다.
- 쓰러짐(잔혹 표현 없음)
  - 모래 떼: 몸을 말고 굴러 달아난 뒤 모래로 흩어집니다.
  - 빛 수호체: 깜박이다 접히며 사라집니다.
  - 경비대원: 주저앉아 보호막 캡슐을 펴고, 습격 뒤 구급 드론이 데려갑니다(3분 뒤 복귀).
  - 탱크: 어두워지고 연기가 납니다. **설계와 다른 점**: 드론이 잔해를 치우는 작업은 만들지 않았습니다. 습격 45초 뒤 끌려간 것처럼 사라지고, 공장이 다시 조립합니다.
- 건물 피해: 경미(그을음·찌그러진 패널) → 연기 → 균열·불꽃·창문 꺼짐 → 뚫린 외벽과 드러난 골조. 수리가 진행되면 서서히 지워집니다.
- 수리: 습격이 끝나면 건설보다 먼저 합니다. 시간은 피해 단계당 40초이고, 단계당 금속 1상자를 씁니다(있을 때).
- 재건: 잔해 → 드론이 치움(30초, 재료 절반이 상자로 돌아옴) → 세 단계(45초씩)로 다시 세움. 돌아온 절반은 재건에 씁니다.
- 회계 불변식: 캔 것 + 회수한 것 = 완성 비용 + 예약 + 재고 + 쓴 것.
- 카메라: 습격 중에는 그 전초기지의 저장소와 전선을 잡습니다. 시작에 한 번 물러나고 끝에 한 번 돌아올 뿐, 전투를 쫓지 않습니다. 확장 장면보다 먼저입니다.
- 습격 중에는 유성과 셔틀을 띄우지 않습니다.
- **만들지 않은 것**: 방어막 발전기(반투명 돔), 습격의 동서남북 방향 문구(문구는 "바깥쪽"으로 씀).

### 6.8 동적 우주 배경 (Phase 9)

| 요소 | 움직임 | 시계 |
|---|---|---|
| 별 | 약하게 깜빡이는 별 30~40개(지금 6개) + 밝기가 천천히 바뀌는 별 몇 개 | t |

| 혜성 | 매우 드물게, 2~3분에 걸쳐 먼 하늘을 천천히 건넘 | 타임라인 RARE |
| 가스 행성 | 고리 행성이 수 시간에 걸쳐 하늘을 천천히 이동, 낮 쪽 면이 해 방향 | W |
| 위성 | 가스 행성 둘레를 도는 작은 위성(주기 약 3시간), 위상 | W |

### 6.9 행성 환경 (Phase 9)

- 먼지 폭풍: 황토색 안개와 비스듬한 먼지 입자, 원경이 흐려짐. 드론은 계속 일합니다(4~6분).
- 유성우: 먼 하늘의 줄기 여러 개, 먼 지면에 작은 먼지 기둥(드문 사건, 약 2분)
- 태양 플레어:
  - 하늘이 40초에 걸쳐 붉어집니다. 번쩍임이 아닙니다.
  - 기지 방어막이 펼쳐지고 드론이 잠시 대피합니다(시뮬레이션 사건, 1~2분).
  - 그날 밤 오로라 확률이 높아집니다.
- 오로라: 밤에 하늘 위쪽의 초록·장미빛 커튼이 천천히 흔들립니다.
- 전기 폭풍: 먼 구름 사이의 희미한 방전(번개와 같은 밝기 제한)

### 6.10 드문 사건 (Phase 9)

대형 우주선 통과, 혜성, 대규모 유성우, 오로라, 외계 함대가 멀리 지나감, 이주선 착륙(단계 8 이상, 구역마다 한 번), 새 위성 발사(단계 9 이상).

**Phase 9에서 구현한 것(6.8~6.10, 5.5)**
- 사건은 모두 `world/events.ts`의 타임라인 사건입니다. W와 시드의 순수 함수이고, 30분 블록마다 하나까지입니다.
  - 자격 조건에 시드를 넘기도록 `EventCtx`에 `seed`를 더했습니다. 무지개는 날씨, 오로라는 앞선 플레어를 봅니다.
  - 블록 결과는 저장해 두고 다시 씁니다.
- 진행 단계가 필요한 사건은 `eventShown(kind, stage)`로 장면, 상태 문구, "자세히"에서 같은 규칙을 씁니다. 사슴 8, 반딧불 무리 4, 고목 개화 9, 이주선 8, 위성 9.
- 상태 문구와 "자세히": 사건이 보이는 동안 그 사건의 문장이 상태 줄에 나오고, "자세히"에 "지금: ○○"이 생깁니다. 습격이 먼저입니다.
- 습격과 겹치지 않음: 습격이 시작될 때(또는 시작 뒤 100초 안에) 우주 사건이 있으면, 그 사건이 끝난 뒤 1분으로 미룹니다(시뮬레이션).
- 태양 플레어 동안 새 일을 받는 드론은 저장소 옆으로 대피합니다. 하던 한 번의 일은 마칩니다. 상자 회계를 깨지 않기 위해서입니다.
- 우주 배경
  - 깜박이는 별 30개(그중 몇은 아주 천천히 밝아졌다 어두워짐)
  - 성운 두 장(아주 느린 밝기 호흡)
  - 가스 행성: 6시간 주기로 모서리 안에서 이동하고, 밝은 쪽이 해를 향합니다.
  - 위성: 3시간에 한 바퀴, 행성 앞뒤를 지납니다.
  - 소행성: 90~180초마다 가스 행성 반대쪽 위 모서리를 지납니다.
- 행성 환경
  - 먼지 폭풍: 땅 쪽이 짙은 황토빛 막 + 땅 위로만 부는 먼지 + 원경이 흐려짐
  - 전기 폭풍: 지평선의 어두운 구름 띠 + 타이머 양옆의 희미한 방전
  - 태양 플레어: 40초에 걸쳐 하늘 위쪽이 붉어짐 + 저장소 위의 낮은 방어막
  - 오로라: 밤하늘 맨 위의 초록·장미빛 커튼
- 하늘의 볼거리: 유성우, 혜성, 대형 우주선, 먼 함대. 모두 상단 바와 타이머 사이의 띠, 또는 타이머 양옆으로만 지나갑니다.
- 땅의 볼거리
  - 이주선: 연병장 뒤에 내려앉았다가 떠나고, 착륙과 이륙 때 먼지가 일어납니다.
  - 위성 발사: 저장소 옆에서 20초 대기 뒤 연기 줄을 남기며 올라갑니다.
- 숲
  - 무지개: 봄·여름, 15분 안에 비가 그쳤고 해가 있을 때. 해 반대쪽, 타이머 옆에 뜹니다.
  - 반딧불 무리: 여름밤에 최대 64마리가 공터 위를 고리 모양으로 돕니다.
  - 첫눈: 그해 첫 눈이 내리기 시작한 뒤 12분 안. 눈 자체는 날씨이고, 이 사건은 문구로 알립니다.
  - 고목 개화: 봄마다 한 블록, 왕관 전체에 분홍 꽃송이와 옅은 분홍 기운이 돕니다.
  - 맑은 밤의 별똥별: Director fx로 50~120초마다 하나씩.

## 7. 집중 보호와 접근성

### 7.1 밝기·번쩍임 제한 (모든 Phase 공통 검수 항목)

- 번개·전기 폭풍:
  - 하늘 영역만 최대 +10% 밝기입니다. 올라갈 때 120ms, 내려갈 때 600ms 이상입니다.
  - 8초에 한 번 이하, 10초에 2회 이하입니다. WCAG 2.3.1(초당 3회)보다 훨씬 낮습니다.
  - 화면 전체가 하얗게 되는 일은 없습니다.
- 태양 플레어·노을·밤 전환은 수십 초~수 분에 걸친 램프입니다.
- 검수할 때 캡처 프레임에서 **프레임 사이 평균 밝기 변화**를 계산해 기록합니다.

### 7.2 타이머 영역 보호

- 입자 밀도: 타이머 사각형(`timerRect`) 안은 ×0.35로 줄입니다.
- 생명체·외계 유닛 경로는 타이머 영역을 피합니다. 가림 페이드(OcclusionFader)는 지금처럼 유지합니다.
- UI 팝업이나 알림은 없습니다. 사건은 상태 문구 한 줄로만 알립니다.

### 7.3 동작 줄이기 (`prefers-reduced-motion` 또는 설정 "애니메이션 끔")

| 항목 | 줄인 모습 |
|---|---|
| 날씨 입자 | 입자 없음. 정지된 옅은 빗줄기 텍스처 / 눈 덮임·젖음 같은 **상태**는 그대로 |
| 카메라 | 이동 없음(지금처럼 하나의 조용한 구도) |
| 유성·혜성·번개 | 표시 안 함 |
| 전투 | 투사체 없음. 외곽의 정지된 외계 무리 표시 + 방어막 돔 + 피해 상태만 |
| 하늘·빛 | 시간대 변화는 유지(1fps로 갱신하므로 계단식이지만 아주 느림) |

### 7.4 숲의 밤과 UI 가독성

숲 UI는 밝은 베일 위에 진한 글씨를 씁니다. 밤의 장면을 너무 어둡게 하면 대비가 깨집니다.

- 숲의 밤은 **달빛 파스텔**로 그립니다. 타이머 주변 하늘 밝기를 일정 수준 이상으로 유지합니다.
- 깊은 밤(하루의 약 15%)에는 `data-light="night"`로 UI 토큰을 우주 테마처럼 밝은 글씨와 어두운 베일로 바꿉니다. CSS로 30초에 걸쳐 전환합니다.
- 검수: 시계 숫자 뒤 픽셀을 채취해 **대비 4.5:1 이상**인지 시간대별로 측정합니다.

## 9. 데이터·결정성·이관

- `SIM_VERSION` 1 → 2: 연못, 고목, 비 → 빗물받이, 자원 4종, 습격, 수리, 재건이 바뀝니다. 체크포인트는 버전이 달라 자동으로 버려지고 다시 계산됩니다.
- **데이터 버전 2 → 3** (11절 결정 5)
  - 새 규칙으로 처음부터 다시 계산하면 같은 W에서도 나무 수와 시설 종류가 달라집니다.
  - 그래서 이관 때 **옛 규칙(시뮬레이션 v1)의 결과를 고정합니다.**
  - 옛 시뮬레이션 코드를 `src/sim/legacy/v1/`에 동결합니다. 이관할 때만 동적으로 불러오는 별도 chunk라서 평소 로딩에는 영향이 없습니다.
  - `world.base`를 테마별 기준점으로 넓힙니다:
    ```ts
    base = { W, forest: { units, partial, stock }, space: { units, kinds[], partial } }
    ```
  - 새 시뮬레이션은 지금의 `legacy` 처리처럼 기준점에서 시작합니다. 완성 수는 유지하고, 옛 시설 종류는 새 건물 종류에 대응시킵니다:
    - 태양광 → 발전기
    - 거주 → 거주
    - 온실 → 온실 돔(추가 종류로 유지)
    - 관측소 → 연구
    - 통신 → 위성 접시
    - 작업장 → 공장
    - 연결 거점 → 사령부
  - 이관 전 원본은 `moa:v3:pre-migration`에 한 번 보관합니다. v2 키는 건드리지 않습니다. 이관은 멱등입니다.
- 키 이름공간은 `moa:v3:*`이고, `?store=`도 그대로 지원합니다.
- 알려진 한계(지난번과 같음): 이관 후에도 열려 있는 옛 버전 탭은 v2 키에 계속 씁니다.
- 결정성 테스트에 추가할 것:
  - 날씨·타임라인 순수성
  - 습격을 포함한 분할 독립성(5분×N = 한 번에)
  - 자원 벡터 회계 불변식(음수 없음, 예약 = 소비 + 남은 몫)
  - 피해 후 수리 완료
  - 콜로니 단계 비감소
  - 이관 전후 완성 수 동일

## 10. 단계별 구현과 검증 계획

모든 화면 검수는 headless Playwright에서 `?store=lw-<phase>-*` 이름공간으로만 합니다. 사용자 브라우저의 기본 저장과 열린 탭은 건드리지 않습니다.

모든 Phase에 공통으로 다음을 합니다.
1. 자동 테스트, 타입 검사, 운영 빌드

3. 정해진 W 지점 스크린숏(데스크톱 1440×820, 모바일 390×844)

6. 동작 줄이기 화면

결과는 Phase마다 이 문서 끝의 "검수 기록"에 그대로 적습니다. 관찰하지 않은 것은 확인했다고 쓰지 않습니다.

## 12. 위험과 한계

- **범위가 큽니다.** 우주 테마(Phase 5~8)는 시뮬레이션과 장면 대부분을 새로 쓰는 일입니다. Phase마다 검수를 통과해야 넘어가므로 시간이 오래 걸립니다.
- 실기기(저사양 노트북·휴대폰) 성능은 이 환경에서 측정할 수 없습니다. CPU 감속은 대용 측정으로만 보고합니다.
- 소리(천둥·전투음)는 범위에 넣지 않았습니다. 지금 사운드는 기본 꺼짐인 앰비언트 2종과 완료음입니다. 넣으려면 따로 정해야 합니다.
- 날씨와 드문 사건은 시드에 따라 정해집니다. 짧게 쓰는 사용자는 드문 사건을 거의 못 볼 수 있는데, 이는 의도한 것입니다("오래 집중했을 때만").
- 독자 디자인 여부는 제가 실루엣·색·이름을 피하는 방식으로 지킵니다. 법적 검토는 아닙니다.

- 시스템(채굴, 단계 건설, 확장, 습격, 수리, 사건)은 있었지만, 그림은 달기지 미감을 거의 그대로 썼습니다.
  - 작업 드론은 바퀴 달린 로버 그림이었고, 건물은 흰 알약 모양에 동그란 창이었습니다.
- 사용자의 세계(누적 69시간)에서 습격은 56번 있었습니다. 모두 DEV 시간 이동 구간 안이라 화면에 나온 적이 없습니다.
- 습격은 포탑 뒤(누적 약 85분)부터 50~90분 간격이었습니다. 5분·25분 세션으로는 거의 볼 수 없습니다.

**바꾼 것: 습격을 세션 길이에 맞춤** (`src/world/pace.ts`, `SIM_VERSION` 11)
- 세계가 세션마다 구간 하나를 기록합니다: 시작 W, 계획 길이(카운트다운 T, 스톱워치는 null), 끝 W. 최근 600개까지 보관합니다.
- 습격 시점은 시드와 이 기록의 순수 함수입니다.

  | 세션 | 습격 |
  |---|---|
  | 5분 | 1분 45초~2분 40초에 시작해 세션 안에 끝남 |
  | 25분 | 9~16분에 한 번 |
  | 긴 세션 | 첫 습격은 16분 안, 그 뒤 30~45분마다 |
  | 스톱워치 | 3~7분에 첫 습격 |
  | 4분 미만 | 없음 |

- 습격 사이는 최소 8분입니다. 5분 세션을 연달아 하면 한 번 걸러 한 번 오고, 습격이 없는 세션에는 행성 사건(혜성, 대형 우주선, 함대, 유성우, 폭풍)이 하나 들어갑니다.
  - 이 사건은 화면 연출 전용이라 시뮬레이션은 모릅니다.
  - 행성 자체의 사건과는 겹치지 않게 놓습니다.
- 세션을 일찍 끝내면 아직 오지 않은 습격만 빠집니다. 과거는 바뀌지 않으므로 체크포인트가 그대로 유효합니다.
  - 저장된 체크포인트에는 그때까지 본 습격의 표지(`raidKey`)를 넣었습니다.
  - 러너는 계획이 과거에서 달라지면 그 앞으로 되돌아갑니다.
- 포탑 전에도 습격이 옵니다. 다만 작은 정찰 무리(모래 떼 3~8마리)뿐이고, 착륙선·사령부의 방어 드론이 막습니다.
- 습격 규모는 습격 횟수가 아니라 콜로니(구역·단계)에 따라 커집니다. 세션 수가 많아도 피해가 계속 커지지 않게 하기 위해서입니다.
- **성장은 그대로입니다.**
  - 수리·잔해 정리·재건은 새로 둔 정비 드론이 맡습니다. 처음 1대, 사령부와 공장으로 각 1대가 늘어 최대 3대입니다.
  - 정비 드론은 상자를 쓰지 않고, 작업 드론은 수리를 하지 않습니다.
  - 그래서 세션을 어떻게 나눠도 건물 완성 시각과 자원은 습격과 무관합니다. 테스트로 확인했습니다.
- DEV: "다음 습격 −10초" 대신 "습격 부르기(10초 뒤)" 버튼을 두었습니다. 상태 줄에 다음 계획 습격과 정비 드론 상태가 나옵니다.

**바꾼 것: 우주 그림을 SF 콜로니로**

### Phase 11-2 — 습격 빈도 올리기 (2026-10-05)

**받은 피드백**: "습격 빈도가 너무 없다. 거의 한 번만 나타나는 느낌이다. 적절한 빈도가 있어야 보는 맛이 있다."

**바꾼 것** (`SIM_VERSION` 12)
- 간격: 세션 중 4~6분 30초마다. 첫 습격은 세션 시작 1분 반~3분 반 사이이고, 스톱워치는 1분 반~3분입니다. 습격 사이는 최소 3분 30초라서, 짧은 세션을 연달아 해도 세션마다 한 번씩 옵니다.
- 두 가지 규모(`sim/raid.ts`)
  - 작은 교전
    - 정찰대: 포탑 전 2~3마리, 그 뒤 3~8마리, 모래 떼만
    - 길이 50~60초
    - 경비대 최대 8명과 탱크 2대만 나가고, 나머지는 연병장에 남음
    - 피해는 건물 하나에 2단계까지, 탱크 무력화와 잔해 없음
  - 큰 습격: 세 번째마다(`fullEvery` 3). 이전 습격과 같이 80~100초이고, 빛 수호체도 오고, 주둔군 전체가 나갑니다.
- 상태 문구를 둘로 나눴습니다. 작은 교전은 "…정찰대가 다가와요 — 방어 드론이 막으러 나가요", 큰 습격은 "…가 대거 몰려와요 — 주둔군이 막으러 나가요"입니다.
- 소개 문구, FAQ, README의 빈도 설명을 바꿨습니다.

**실제로 확인한 것**
- 자동 테스트 121개 통과
  - 바뀐 기대값
    - 5분 세션 24개에 습격 24번
    - 25분 세션은 3~5번
    - 2시간은 15번 이상, 간격 3.5~14분
    - 스톱워치 첫 습격 1.5~3분
  - 작은 교전은 50~60초이고, 피해 2단계 이하, 잔해 없음
  - 습격이 있어도 성장은 같음(그대로 통과)
- 시뮬레이션 측정(시드 3개 × 6시간, 연속 세션)

  | 세션 | 세션당 습격 | 큰 습격 |
  |---|---|---|
  | 5분 | 0.94번 | 204번 중 67번 |
  | 25분 | 3.96번 | 178번 중 58번 |

  - 5분 세션이 1번에 조금 못 미치는 건, 첫 건물이 서기 전(첫 약 10분)의 습격을 건너뛰기 때문입니다.
  - 모든 습격이 건물에 피해를 남겨, 정비 드론의 수리가 자주 보입니다.
  - 이 18시간 동안 잔해(건물 소실)는 0번이었습니다. 다른 시드를 24시간 돌린 테스트에서는 잔해와 재건을 확인했습니다.

**남은 점**
- 실제 속도로 25분 동안 습격이 몇 번 보이는지는 녹화로 확인하지 않았습니다. 횟수는 시뮬레이션 측정값입니다.
